# إنشاء نسخة عميل جديدة (Tenant Provisioning)

## متى تُستدعى
عند طلب "أنشئ نسخة لمدرسة جديدة" أو ما شابه، أو عند تطوير/تحسين سكربت الأتمتة المستقبلي لهذه العملية.

## المتطلبات المسبقة (Preconditions)
- Deployment Template (الكود الأساسي) مستقر وخالٍ من مشاكل معروفة
- معلومات العميل الجديد متوفرة: اسم المدرسة، الدولة (تحدد بوابة الدفع: PayTabs/Stripe/يدوي)، الشعار، الألوان الأساسية

## خطوات التنفيذ (شبه يدوية بهذه المرحلة — راجع DECISIONS.md)
1. Clone المستودع الأساسي (Deployment Template) بمستودع Git جديد خاص بهذه المدرسة
2. إنشاء مشروع Supabase جديد (قاعدة بيانات مستقلة تماماً)
3. تشغيل `npx prisma migrate deploy` على القاعدة الجديدة
4. تشغيل Seed الأساسي (الأدوار + حساب Admin أولي فقط — لا بيانات وهمية)
5. ضبط متغيرات البيئة بمنصة الاستضافة (Vercel): اتصال قاعدة البيانات، دولة العميل (لتحديد مسار الدفع)، بيانات بوابة الدفع المناسبة
6. نشر (Deploy) المشروع وربط الدومين
7. تسجيل الدخول كـ Admin أولي والتحقق من ظهور شعار/اسم المدرسة الافتراضي بشكل صحيح
8. تسليم بيانات الدخول الأولية للعميل بقناة آمنة (لا بريد إلكتروني عادي بالنص الصريح لكلمة مرور دائمة — كلمة مرور مؤقتة تُغيَّر بأول دخول)

## قواعد
- لا تُنشأ نسخة جديدة بدون التحقق أولاً أن آخر إصدار من الكود مستقر (لا Known Issues حرجة بـ STATUS.md)
- كل نسخة جديدة تُسجَّل (اسم العميل، تاريخ الإنشاء، الدولة) بسجل داخلي بسيط (يُنشأ عند أول عميل فعلي — لا يوجد بعد بمرحلة التخطيط هذه)

## الناتج المتوقع
نسخة عاملة بالكامل، تسجيل دخول Admin ناجح، شعار/بيانات المدرسة صحيحة، وتأكيد أن بوابة الدفع المناسبة لدولة هذا العميل مفعّلة (أو التسوية اليدوية مفعّلة إن كانت سوريا).
