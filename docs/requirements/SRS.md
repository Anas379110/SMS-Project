## 1. Functional Requirements

### FR-1 — إدارة الهوية والوصول (Auth & Access)
- FR-1.1: تسجيل دخول بأدوار (Admin/Teacher/Parent/Student/Accountant) بحساب بريد إلكتروني/كلمة مرور
- FR-1.2: كل دور يرى فقط البيانات والصلاحيات المرتبطة به (RBAC)
- FR-1.3: إعادة تعيين كلمة المرور عبر بريد إلكتروني
- FR-1.4: كل نسخة (Deployment) معزولة بالكامل عن نسخ المدارس الأخرى (True White-label)

### FR-2 — إعداد المدرسة (Branding)
- FR-2.1: الأدمن يستطيع رفع شعار المدرسة وتحديد الألوان الأساسية
- FR-2.2: عرض اسم المدرسة بالواجهة وبكل المستندات المُصدرة (فواتير، تقارير)

### FR-3 — إدارة الطلاب والفصول
- FR-3.1: إضافة/تعديل/أرشفة طالب (بيانات أساسية + ولي أمر مرتبط)
- FR-3.2: إنشاء فصول دراسية وتعيين طلاب لها
- FR-3.3: تعيين معلمين لفصول/مواد محددة

### FR-4 — الحضور
- FR-4.1: المعلم يسجل حضور/غياب/تأخر لكل طالب بالفصل يومياً
- FR-4.2: عرض سجل حضور الطالب تراكمياً (Admin/Parent/Student)
- FR-4.3: إشعار ولي الأمر عند تسجيل غياب

### FR-5 — الدرجات
- FR-5.1: المعلم يرصد درجات لمادة/تقييم محدد
- FR-5.2: عرض كشف درجات للطالب (Parent/Student/Admin)
- FR-5.3: إشعار ولي الأمر عند إضافة درجة جديدة

### FR-6 — الجدول الدراسي
- FR-6.1: الأدمن يُدخل جدول الحصص لكل فصل (عرض فقط بهذا الإصدار — بدون محرك جدولة آلي)
- FR-6.2: عرض الجدول لكل دور حسب صلاحيته

### FR-7 — المالي (Fees & Invoicing)
- FR-7.1: الأدمن/المحاسب يعرّف بنود رسوم لكل مستوى دراسي
- FR-7.2: إصدار فاتورة لطالب (يدوياً أو دفعة واحدة لكل الفصل)
- FR-7.3: تسجيل دفعة — تلقائياً (خليج/UK/US عبر بوابة دفع) أو **يدوياً** (سوريا/العراق بالمرحلة الأولى، راجع DECISIONS.md)
- FR-7.4: تقرير مالي بسيط (مستحقات/مدفوعات) للمحاسب

### FR-8 — الإشعارات
- FR-8.1: إشعار داخل النظام على الأقل (بريد إلكتروني إن سمحت البنية التحتية المجانية) لأحداث: غياب، درجة جديدة، فاتورة جديدة

## 2. Non-Functional Requirements

| البند | المتطلب |
|---|---|
| **Performance** | زمن استجابة API < 500ms على Free Tier (هدف واقعي، أعلى من معيار الإنتاج المثالي بسبب قيود الاستضافة المجانية) |
| **Security** | عزل بيانات كامل بين النسخ (فيزيائي أصلاً بحكم True White-label)، تشفير كلمات المرور (bcrypt/argon2)، HTTPS إجباري |
| **Availability** | لا SLA مضمون بمرحلة Free Tier — يُوثّق كقيد معروف للعميل التجريبي |
| **Scalability** | كل نسخة تخدم مدرسة واحدة (نطاق محدود طبيعياً) — لا حاجة تصميم لتوسع أفقي ضخم بهذه المرحلة |
| **i18n / Localization** | عربي وإنجليزي كاملان، RTL/LTR ديناميكي، لا نصوص Hardcoded |
| **Accessibility** | WCAG 2.1 AA كحد أدنى (هدف — قد يُخفَّف لبعض التفاصيل الدقيقة بضغط الوقت، يُوثّق أي استثناء) |
| **Maintainability** | Deployment Template موحّد وموثّق — أي مطور جديد يفهم كيف يُنشئ نسخة جديدة خلال ساعة |
| **Reliability** | نسخ احتياطي يومي لقاعدة بيانات كل عميل (حتى على Free Tier إن أمكن، أو يدوي مبدئياً) |

## 3. User Stories (عيّنة من كل وحدة Must — تُستكمل تدريجياً أثناء التطوير)

### Auth
```
كـ: مدير مدرسة (Admin)
أريد: تسجيل دخول آمن بحسابي
حتى: أدير بيانات مدرستي دون قلق من وصول غير مصرح

Acceptance Criteria:
- تسجيل دخول ببريد/كلمة مرور صحيحين ينجح
- محاولة دخول ببيانات خاطئة تُرفض برسالة واضحة (لا تكشف أيهما خاطئ: البريد أم كلمة المرور)
- الجلسة تنتهي تلقائياً بعد فترة خمول محددة
```

### الحضور
```
كـ: معلم
أريد: تسجيل حضور فصلي كاملاً خلال أقل من دقيقة
حتى: لا أستهلك وقت الحصة بالإجراءات الإدارية

Acceptance Criteria:
- عرض قائمة كل طلاب الفصل بشاشة واحدة
- تحديد الحالة (حاضر/غائب/متأخر) لكل طالب بنقرة واحدة
- حفظ السجل يُطلق إشعاراً تلقائياً لأولياء أمور الغائبين
```

### المالي
```
كـ: محاسب المدرسة
أريد: إصدار فاتورة لطالب وتسجيل دفعته
حتى: أتابع المستحقات المالية بدقة دون دفاتر يدوية

Acceptance Criteria:
- إصدار فاتورة يحدد البند، المبلغ، تاريخ الاستحقاق
- تسجيل دفعة (تلقائي عبر بوابة أو يدوي حسب الدولة) يحدّث حالة الفاتورة فوراً
- تقرير المستحقات يعكس الحالة الفعلية بلا تأخير
```

**(باقي User Stories الكاملة لكل FR تُكتب تدريجياً بمرحلة Development لكل Feature — Rule 51/52: Definition of Ready/Done يفرض وجود User Story وAcceptance Criteria قبل بدء أي Task فعلياً)**

## 4. Use Cases (نموذج واحد تفصيلي كمرجع للبقية)

**Use Case: تسجيل حضور الفصل**
- **Actor:** Teacher
- **Trigger:** بداية الحصة الدراسية
- **Preconditions:** المعلم مسجل دخول، الفصل معرّف بالنظام، الطلاب مسجلون بالفصل
- **Main Flow:**
  1. المعلم يفتح صفحة "تسجيل الحضور" لفصله
  2. النظام يعرض قائمة الطلاب بحالة افتراضية "حاضر"
  3. المعلم يعدّل حالة أي طالب غائب/متأخر
  4. المعلم يضغط "حفظ"
  5. النظام يحفظ السجل ويرسل إشعارات للغائبين
- **Alternative Flow:** المعلم يعدّل سجل حضور سابق بنفس اليوم (قبل إغلاق اليوم الدراسي)
- **Error Flow:** فقدان الاتصال أثناء الحفظ → النظام يحتفظ بالتغييرات محلياً ويعيد المحاولة تلقائياً
- **Postconditions:** سجل حضور اليوم محفوظ ومرئي لكل الأدوار المصرح لها
