# SDLC.md — اختيار نموذج دورة حياة التطوير

## معطيات القرار
- فريق صغير جداً / فردي على الأرجح (استُنتج من قرار Free Tier + عدم ذكر فريق)
- جدول زمني ضيق نسبياً: 3 أشهر لـ MLP
- متطلبات ستتضح تدريجياً أثناء البناء (خصوصاً تفاصيل المالي متعدد الدول وProvisioning)
- الهدف جودة تجربة عالية (MLP) لا مجرد إثبات تقني (MVP)

## المقارنة

| النموذج | الأداء بمعطيات هذا المشروع |
|---|---|
| **Waterfall** | ❌ يفترض متطلبات ثابتة من البداية — متطلباتنا (خصوصاً المالي/Provisioning) ستتضح تدريجياً |
| **V-Model** | ❌ صارم وثقيل الحوكمة — غير مناسب لفريق صغير بجدول ضيق |
| **Spiral** | ❌ مصمم لمشاريع كبيرة عالية المخاطر بميزانية أكبر لتحليل مخاطر متكرر رسمي |
| **RAD** | ⚠️ مناسب جزئياً (سرعة) لكنه يفترض أدوات جاهزة كثيرة تقلل التحكم بالتفاصيل — المالي وProvisioning يحتاجان دقة أعلى من Boilerplate جاهز |
| **Scrum الكامل (Sprints + كل الاجتماعات الرسمية)** | ⚠️ ثقيل الحوكمة لفريق فردي/صغير جداً — طقوس Scrum مصممة لفرق متعددة الأعضاء |
| **Kanban** | ✅ مرن، يناسب فريقاً صغيراً، يسمح بإعادة ترتيب الأولوية بسرعة عند اكتشاف تعقيد جديد (مثال: بحث بوابات الدفع بسوريا/العراق) |
| **Agile خفيف (Lean/Incremental بدون طقوس Scrum الكاملة)** | ✅ الأنسب — تسليم تدريجي لكل وحدة (Auth → طلاب/حضور → درجات → مالي)، مراجعة مستمرة، دون عبء اجتماعات فريق غير موجود |

## القرار

**النموذج المعتمد: Agile خفيف (Lean) + Kanban للتتبع اليومي، بدون طقوس Scrum الرسمية الكاملة.**

### آلية العمل العملية
- تقسيم العمل لوحدات تسليم صغيرة (Increments) حسب ترتيب `SCOPE.md`: Auth/Branding → Students/Classes → Attendance → Grades → Schedule (عرض) → Financial
- كل Increment: Requirement → Design صغير → Implementation → Test → Security Review → Commit (دورة القسم 37 بالتعليمات الأساسية)
- لوحة Kanban بسيطة بـ`TASKS.md` (To Do / In Progress / Done) بدل أداة خارجية بهذه المرحلة (تُضاف أداة مثل Linear لاحقاً عند نمو الفريق)
- مراجعة أسبوعية ذاتية (بديل Sprint Review) لمقارنة التقدم الفعلي بـ 3 أشهر المتاحة، وتعديل الأولويات إن لزم

### لماذا لا Scrum الكامل؟
طقوس Scrum (Daily Standup، Sprint Planning الرسمي، Retrospective) مصممة لتنسيق فرق متعددة الأعضاء. بفريق فردي/صغير جداً، هذه الطقوس تصبح عبئاً إدارياً بلا فائدة تنسيقية حقيقية — نأخذ **مبدأ** Agile (تسليم تدريجي، تكيّف مستمر) دون **حوكمة** Scrum الثقيلة.

### إدارة التغيير
أي متطلب جديد يظهر أثناء التطوير (خصوصاً بمنطقة المخاطر المعروفة: بوابات الدفع سوريا/العراق، آلية Provisioning) يُقيّم فوراً بـ Impact Analysis مصغّر (الوقت المتبقي من 3 أشهر تحديداً) ويُوثّق بـ `DECISIONS.md` قبل التنفيذ — لا تغييرات صامتة بالنطاق.

### نقطة تحوّل مستقبلية
إذا كبر الفريق لاحقاً (أكثر من 2-3 مطورين)، يُعاد تقييم الانتقال لـ Scrum كامل أو Scrumban — يُوثّق كقرار منفصل حينها، لا يُفترض تلقائياً الآن.
